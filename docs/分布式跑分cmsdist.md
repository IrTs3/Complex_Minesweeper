# 分布式求解器跑分（cmsdist）

> 公开调度服务 **https://ty0712.com:12712**（TLS，2026-11-05 起；明文 7120 已收回环）。
> 把 `solver` 的免猜率统计从单机拆成众包：任何人拿到客户端、**无需任何密钥**，
> `--name 名字` 就能领任务跑分；服务器管任务分发与结果存储，本机 ctlui 管看板。
> 组件都在 `tools/`（`dist_server.py` / `dist_client.py` / `distctl.py` / `ctl_ui.py` + `ctlui/` / `ed25519.py`），
> 脚本在 `scripts/dist/`。

## 一、为什么是分布式

第四代宽 9 解锁后单局最坏 27s，Hard 500 局单机要跑 3~4 小时，专家盘 30×16×99
（`--expert`）更慢；而验收「分层 + 宽 9 到底带来多少胜率」需要**几百上千局的配对样本**。
单机排期排不下，就做成众包：多台机器并行领任务，结果统一回收、按求解器版本归因。

设计约束（全部已落地）：

- **客户端零密钥**：测试者拿到 dmg/zip 双击就能跑，不用申请任何凭据。
  防护不靠鉴权，靠「任务绑定随机 nonce + 严格 schema 校验 + 每 IP 并发上限 + 租约自愈」。
- **结果可按版本归因**：每个 solver 二进制烙进**源码指纹**（见第五节），
  混跑期新旧版本的结果一眼能分开——不然众包数据没法用。
- **能远程修客户端**：测试者不懂技术，出问题必须能自动更新（见第六节，Ed25519 签名链路）。

## 二、任务协议（服务器 → 客户端）

服务器 `tools/dist_server.py`（systemd `cmsdist`，状态目录 `/var/lib/cmsdist`，见 `scripts/dist/deploy-dist.sh`）。
任务体固定 7 个字段，客户端只认字段、不做本地推断：

```json
{"task_id": "20261888", "seed": 20261888, "model": "complex",
 "cols": 30, "rows": 16, "mines": 99, "games": 100}
```

端点一览（全部明文 HTTP，公开端口，业务侧**没有任何 token**）：

| 端点 | 方向 | 作用 |
| --- | --- | --- |
| `GET /ping` | 探活 | 返回队列/在跑/完成计数；Healthchecks 第 9 项打这个 |
| `POST /claim` | 客户端领任务 | 优先队列有货先发队列里的，否则按默认任务流生成新种子；返回任务 + **一次性 nonce** + `pomo`（调度番茄钟相位，见下）；番茄钟休息段/手动暂停都回 `{"paused": true, "reason": …}` |
| `POST /progress` | 心跳（10s 一次） | best-effort 报 x/y + eta；nonce 对上才记。**同时刷新租约存活时钟**——活着就永不被收走，lease 量的是「失联多久」不是「总共跑了多久」 |
| `POST /result` | 客户端交结果 | 必须带同一个 nonce；逐局记录做 schema 校验（字段集合、非负、`guess==mid+end`、`g` 序号连续、`sec≤3600`） |
| `POST /release` | 主动放弃 | 第二段 Ctrl+C 用；nonce 对上就立刻回队列，不用等租约到期 |
| `GET /client/manifest`、`GET /client/file/<名>` | 自动更新 | 签名清单与二进制分发（第六节）；文件名白名单正则 + realpath 双闸防穿越 |

### 调度番茄钟：全舰队按墙上时钟统一歇（2026-11-03）

起因：跑分机一直满载会把笔记本烫到降频。第一版把番茄钟做在 solver 里（本机连算计时，见第三节），
用户当场把口径挪到调度侧——**番茄钟管的是「什么时候发任务」**，单机计时只算第二层兜底。

实现上没有定时器、没有 cron、没有后台线程：`pomo_phase(cfg, now)` 是一个**纯函数**，
按墙上时钟算相位 `pos = (now - anchor) % (work + rest)`，`pos >= work` 即在休息段。
所以服务重启、机器换一批都不影响节拍，全舰队自然对齐。到点做两件事：

1. **`/claim` 拒发**：复用「手动暂停」那一条**不写盘**分支（`_skip_save`），
   回 `{"paused": true, "reason": "pomodoro", "rest_left": 秒}`。客户端据此显示
   「☕ 休息一下，还剩 mm:ss（N 秒后再查）」——`reason` 是 `manual` 时才说「服务器已暂停发放」，
   因为那不是休息，是别来占机器。轮询白烧 CPU 的那条老路（每次拒发重写 ~935KB 的 `state.json`）不许复活。
2. **正在跑的那单在局与局之间睡**：`/claim` 成功时把相位随任务下发（`pomo` 字段），
   客户端换算到**本机时钟域**（`anchor + (本机 now - 服务器 server_now)`，机房没对时也不会错开相位），
   再以 `--pomodoro-phase <anchor>:<连算>:<整轮>` 交给 solver。solver 在每个局间重算相位，
   落在休息段就睡到这段结束——**进程不死，100 局跑到 51 局停下，歇完接着跑 52–100，不重来**。
   休息行因此带 `"src": "sched"`（调度定的）或 `"local"`（本机计时到点），面板据此说「调度定的」/「已连算 mm:ss」。

三条边界：`off` 只影响**之后领的任务**（已领的按它领到的时刻表走完，硬杀=整任务作废，不划算）；
`on`/`set` 把 anchor 拨到此刻（不重拨的话一步就跨进休息段，管理员刚按下开就看到全舰队停摆）；
进度上报在休息期照发，租约不会被误收。时长解析与服务端 `pomo_dur`、客户端 `pomo_parse`、
solver `parseDur` 是同一把尺的三份拷贝（分发形态逼的），由 `check_invariants.py` 第 13 组逐条钉住。

入口：`distctl.py pomo on [25m/5m] | off | set <连算>/<休息> | status`，
ctlui「队列与结果」卡里一组开关 + 两个时长框 + 本地一秒一跳的倒计时（`d.pomo` 随 `admin-lite` 带回）。
`distctl.py status` 第一屏就报此刻在连算还是在休息、还剩多久 —— 终端里只看「运行中/已暂停」
会把「节拍到点自动歇」整个看漏，那两种停的原因不一样、要做的事也不一样。
一轮（连算+休息）低于 60 秒直接拒：歇得太碎，交结果的开销比算得还多。

上线状态（2026-11-03）：调度端已 `deploy-dist.sh` 推到 ECS 并重启 `cmsdist`（`distctl.py status`
读回「番茄钟: 未开（任务一直发）；两段时长记为 连算 25m00s / 歇 5m00s」= 配置在、开关没按）；
三平台包已重打发布，manifest `ver=1793714752 / solver=7d9d7749`。此刻全舰队默认不歇 ——
要歇得有人在 ctlui 或 `distctl pomo on` 把它打开。

**nonce 是防作弊的核心**：服务器为每次领取生成 `secrets.token_hex(16)`，
结果必须出示领取时那份。所以：
- 伪造别人的结果？不知道对方从 `/claim` 拿到的 nonce。
- 重复提交同一结果刷胜率？`task_id` 已进 done 就 409 拒收。
- 想改参数（`--expert` 偷偷跑更大的盘）？回来交结果时按 `task_id` 查的是**服务器存的原任务参数**，对不上直接判无效。

**TLS 入口（2026-11-05，方案一）**：明文 HTTP 上中间人能截 `/claim` 回复拿到
nonce 再灌假结果——堵法是把 7120 藏到 nginx 后面，`https://ty0712.com:12712`
对外的证书与主站同一张（续期自动跟上）。客户端默认地址已改 12712。
**2026-11-05 换代完成已收口**：7120 绑回环 + ufw 撤规则（安全组那条手动删），
公网只剩 12712 一条路；没换上包的机器（那台 Air）靠人手动重装，连不上明文口是预期行为。
反代后的真实 IP 靠 nginx 发的 `X-Real-IP`——服务器只信回环对端发的这个头
（`_ip`，公网直连 7120 伪造无效），每 IP 并发上限 / 下载配额 / done 记录都靠它。

租约自愈：`/claim` 后超过 `lease_sec`（默认 2h，`admin-lease` 可调）没交结果的，
`/ping` 和每次领用时会触发回收，任务重回队列并进入 `cool_sec` 冷却（默认 60s，
给管理员留删除窗口，避免刚收回就被同一个慢客户端再领走）。

**首心跳宽限（2026-11-05）**：从未上报过进度的任务不按整份租约等——客户端领完
10 秒内就会报第一次进度，15 分钟（`HEARTBEAT_GRACE_SEC`）还一声没有按「领完就死」
收回重发，名额不再白占 2h。同一任务空转满 3 次（`HEARTBEAT_MISS_CAP`）仍无心跳的
退回整份租约：老客户端压根不发进度，一直按宽限收会把它们打成无限重发循环。
ctlui 进行中表把超宽限的未上报行整行浅黄（低于离线两级，悬停有说明）。

结果落盘为 `results/<task_id>.json.gz`，`done` 索引里带 `solver_ver` / `client_ver` / `ip` / `name` / `os` /
`wins` / `zeroGuessWins` / `guessTrap`，以及 `valid` 标记——`admin-invalidate` 只置 false，
原始文件保留可复核。两个身份各管一半（求解器 / 客户端程序字节），见第六节。

## 三、客户端（测试者视角）

`tools/dist_client.py` → 打成三平台成品（`scripts/dist/package-dist-client.sh`，产物进 `dist-solver/`，已 gitignore）：

| 平台 | 形态 | 说明 |
| --- | --- | --- |
| macOS | `cmsdist-client-macOS.dmg` | PyInstaller **onefile** 单二进制，内嵌 solver |
| Windows | `cmsdist-client-win64.zip` | 免安装：Python embeddable 3.13.9 + `dist_client.py` + `solver.exe` + `开始跑分.bat` |
| Linux | `cmsdist-client-linux64.tar.gz` | 免安装：`dist_client.py` + `solver-linux`，需要系统 python3 |

主循环：领任务 → 起 solver 子进程逐局读 JSONL → **终端实时面板** → 交结果 → 领下一个。
细节都在这份文件里，几条对外的行为契约值得记：

- **两段式 Ctrl+C**：第一段=跑完当前局再退，已跑的局不丢；第二段=杀掉 solver 并 `/release` 放弃任务。
- **本机番茄钟 `--pomodoro`（2026-11-03，默认 `25m/5m`，`off` 关）**：连算满指定时长就在
  **局与局之间**歇一段，免得笔记本一直满载把机器烫到降频。这是**第二层**——调度侧的全局节拍在第二节。
  三条不可让的边界：
  ① **绝不跨局停**——休息只落在两局之间，最后一局算完不再歇（中途停 = 客户端判「solver 提前结束 →
  整任务作废」，已跑的局全扔）；② 休息行 `{"rest":秒,"ran_ms":毫秒,"src":"local|sched"}` 是控制行，客户端在 `records.append`
  之前拦下，**不算一局**（局数一超，服务器按「records 数量不符」400 拒收）；③ 时长解析三份拷贝
  （solver 的 `parseDur` / 客户端的 `pomo_parse` / 服务端 `pomo_dur`），口径必须一致：`1h30m`/`45m`/`90s`/裸数字=分钟/`off`，
  客户端把它归一成 `<秒>s/<秒>s` 再转给 solver，写错当场退出，绝不放过一个 solver 读不懂的参数。
  面板在歇的时候把那行换成「☕ 休息一下 剩余 mm:ss（已连算 mm:ss ｜ 调度定的，#N 局歇完再开）」，
  到点但还没跑完这局时说「☕ 该休息一下了：这局算完就睡，还剩 mm:ss」，且歇掉的秒数从
  「本局已跑」里扣走（不扣的话一次 5 分钟休息能把预估剩余时间直接砍到 0）。solver 手跑那行的
  「已连算」也是 mm:ss，两端同一格式。
  传参前先跑 `probe_pomodoro()`：一次探两个参数（`--pomodoro` + `--pomodoro-phase`），旧包的 solver 都不认；
  硬传过去是「用法退出 → 0 局 → 作废 → 再领」的空转，探出来就降级为两个都不开并说出来，等自更新换上 solver 再生效。
  双击 `开始跑分.bat` / `.command` 的人没法带参数，所以节奏也认环境变量 `CMS_POMODORO`
  （命令行 > 环境变量 > 默认 `25m/5m`）；solver 自己认同一个变量，客户端总把最终值显式传下去（关就显式传 `off`），
  两边不会各读各的。进度上报（10s 一次）在休息期照常发，租约不会被误收。
- **断网不丢数据**：结果先落 `~/dist-pending/`，下次（或后台补报线程）自动重传。
- **后台模式三件套**：`--detach` 脱离终端（日志 `~/cmsdist-client.log`，进度照常 10s 上报，ctlui 上全局面板可见）、
  `--status` 探活 + 日志尾部、`--stop` 跑完当前任务、交了结果再退——**绝不跨任务硬杀**。
  解决的是测试者「终端窗口一堆/不敢关」的问题。
- **预估剩余时间**：`本任务已完成所有局的均值 × 剩余局数(含当前局) − 当前局已跑`，负数封 0，攒够 5 局才给。
  均值口径 2026-11-01 定稿：**用全部已完成局，不用「最近 20 局」滑动窗口**（单局离群由倒计时形态吸收，
  不再让最后 20 局单独决定全程）。实现收在 `_eta_sec(st)` 一处，面板、`/progress` 上报的 `eta_sec`、
  Ctrl+C 提示三条读数同源——两处数字不一样会被当成 bug。
- **面板实时显示 solver 的 RSS**（进行中那行 mac/Linux 走 `ps -o rss=`、Windows 走 PSAPI；
  任务结束那行的峰值 mac/Linux 走 `getrusage(RUSAGE_CHILDREN)`，Windows 没有 `resource` 模块
  → 用客户端自己在实时读数里记下的最大值 `_peak`，来自 PSAPI 的 `PeakWorkingSetSize`）。
  标签写「本任务solver RAM」，口径是**进程级高水位，不是当前这局的用量**：一个任务共用一个 solver
  进程，分层 DP 在最硬那局要过的页还回分配器但不还内核，所以这个数只升不降。
  实测（30×16×99 complex，seed 20264896，二进制 `c1f60148`，12 局）：前 3 局 25–26MB，
  第 4 局（508s，第一次触发宽9分层）跳到 120MB，之后 8 局合计只再涨 4MB —— **不是泄漏**。
  上限由 `kLayerMemCap`（600MB 消息表 + km/lb/卷积临时量，验收线 1GB）决定，所以 100 局任务里
  出现几百 MB 属设计内。是观测，不是限杀守卫。
- **面板宽度**：CJK 按 2 列算，且永远留最后一列不写满（写满部分终端会挂起换行，把面板重画撞歪）。

## 四、管理入口（三选一，权限同一份）

管理操作**不走 HTTP**：本机 `ssh -p <SSH端口> root@…` 调 `dist_server.py` 的 `admin-*` 子命令，
同一份 scrypt 管理口令与 cmsgate 闸门共用（参数逐字一致）。状态文件由 `flock` 串行化，
多入口并发不会踩坏。

| 入口 | 形态 | 适用 |
| --- | --- | --- |
| `python3 tools/distctl.py <cmd>` | 本机 CLI | SSH/终端环境，脚本化 |
| `ctlui`（`tools/ctl_ui.py` + `tools/ctlui/`，默认 127.0.0.1:8712） | 本地网页看板 | 日常看盘 + 少量操作 |
| `python3 tools/dist_server.py admin-status` 等 | 服务器上 root 直接跑 | 应急（前两个都不可用时） |

**2026-10-31 裁决：除 `status` / `export` 外所有管理操作一律要口令**，
服务器端 `needs_pw` 与本机 `GUARDED` 集合保持同步。
ctlui 转调 distctl 复用同一份 SSH 目标与 argv 转义（`remote_argv` 只此一份，防漂移），
口令走 stdin 喂给 ssh——**不进 argv、不进日志、不落盘**。
调度番茄钟也按这条走：`distctl.py pomo on [25m/5m] | off | set <连算>/<休息> | status`
（`admin-pomo`，要口令）。

ctlui 前端卡片：优先队列 / 在跑 / 完成 + 结果筛选与翻页弹窗（历史） + **求解器版本**卡。
「队列与结果」卡里有一组**调度番茄钟**（第二节）：开/关按钮 + 两个时长框 + 一行状态。
状态是本地一秒一跳的倒计时（数据 15 秒才回一次，不动的话看着像卡死），
`in_rest` 那半句写「☕ 休息一下，mm:ss 后恢复发放」；两个时长框回填整分钟走 `25m/1h30m`、
非整分钟走 `90s`，一轮不足 60 秒当场拒绝并把下限说出来。
「开」一次按下就把时长和开关一起写（`pomo on <时长>`），不要求管理员按两遍、输两遍口令。

**休息段「现在不发任务」的三处明显标志**（2026-11-04 用户指出「界面上没有明显标志，也没办法知道
什么时候再发」——原来只有上面那行小灰字，埋在表单末尾，扫一眼根本看不见）：
1. 顶部「调度状态」卡多一格**发货节拍**：休息段黄底 `☕ 休息中 · 00:21 恢复发放（还剩 3:32）`，
   连算段绿底 `▶ 连算中 · 00:39 起歇（还剩 21:00）`，没开则 `未开 · 任务一直发`。
   **给钟点不只给倒计时**：「还剩 3:41」还得自己算几点结束，「14:07 恢复发放」不用；两个都给。
   钟点由 `本机现在 + left` 算，不碰服务器时钟域（`anchor`/`server_now` 那套换算是客户端的事）。
2. 「优先队列」卡头下挂一条整宽黄条，把同一句话说全：这段时间不发新任务、队列里的照常等着、
   正在跑的那单在两局之间睡到这一刻（进程不死、已算的局不丢）、要一直发就把番茄钟关掉。
   挂在队列卡是因为盯队列的人看的是那张卡。
3. 休息段把「暂停发放」按钮**置灰**并在 title 里说明「本来就不发新任务（不是暂停）」——
   否则管理员按下去看不出任何差别，回头还会以为是自己按了暂停。
   置灰**只认番茄钟休息段**：管理员手动暂停（`cfg.paused`）时这个按钮是唯一的恢复入口，绝不能禁。

「优先队列」「最近结果」「版本身份」三张卡同一个形态：**卡面只放前 10 行**（队列按发放顺序、
结果按时间倒序、版本按最新），筛选、翻页和批量删除都收在右上的弹窗里，分页器三处共用一份实现。
顶栏（状态 + 刷新）与弹窗内的表头都冻结，滚动不消失。
版本身份卡显示**两个身份**（求解器源码指纹 + 客户端程序字节哈希，见第六节）的三口径：
「线上在跑」按 `求解器 · 客户端` **成对**聚合终端数、「已发布」求解器一个 + 客户端三平台各一份、
「工作区」两个都实算（含未提交改动，脏时提示），外加一张**两个身份共用**的版本历史表：
每行 `求解器 | 客户端 | 提交 | 时间 | 说明`，按「任一身份变了就收一条」收录；
客户端文件 2026-10-31 才进仓库，更早的提交那一格是 `—`。
数据由 `/api/solver-history` 现算：`git log` 同时跟着求解器那 5 个指纹路径和 `tools/dist_client.py`，
对每个提交按第五节同算法重算内容哈希，去重只留变化点（按 `(求解器, 客户端)` 这一对），
结果按 HEAD 缓存（改代码后 HEAD 变了自动重算；冷算约 3s）。

**刷新为什么走两条命令**（2026-11-02 实测定案，别改回去）：一次刷新 = 一次 ssh，
`admin-status` 全量 741KB（gzip 71KB），其中 `done` 逐条明细占 92%。拆开量——握手 0.27s、
远端生成 0.4s（五次全稳），**传输段却要 1.7~5.0s**：这台 ECS 的公网链路只有 15~40KB/s，
还要和在线客户端抢。所以慢的不是服务器也不是没压缩（`-C` 已把 741KB 压到 71KB，
ControlMaster 复用连接实测无效），是**字节数**。于是：

| 路径 | 命令 | 体积（gzip） | 何时走 |
| --- | --- | --- | --- |
| 看板热路径 | `admin-lite [N]`：config + 队列 + 进行中 + 最近 N 条结果 + **模式×规格聚合** | **~1KB** | 每 15 秒自动刷、点「立即刷新」 |
| 完整历史 | `admin-history`：全量 `done`，只投影 UI 字段（`file`/`claimed_at` 这些不发） | ~28KB | 只在看「历史记录」弹窗时拉一次 |

合计卡的账改由服务器算（`agg_spec`，含精确任务/局数/胜数、已作废不计），前端不再从明细里凑；
`admin-status` 保持全量原样——`distctl` CLI 和 `export` 的口径不能跟着瘦。
T67 把这些钉成回归：热路径塞回全量、或 `admin-lite` 的包超过 8KB，测试直接红。

> ⚠️ **Python 不热加载**：改 `ctl_ui.py` 必须重启进程；`ctlui/` 下前端三件套每次请求从磁盘读，刷新即生效。
>
> 两种「你看到的是旧的」都由 `status` 回执里的 `stale` / `assets_ver` 自己吭声（2026-11-03）：
> 前者 = `ctl_ui.py` 比进程新 → 「重启 ctlui 进程才生效（刷新浏览器没用）」；
> 后者 = 磁盘上的前端三件套换了代 → 「刷新浏览器（Cmd/Ctrl+R）就换成新页面」。
> `assets_ver` 是这三份文件 mtime+体积的短哈希（只 stat，不读内容——这条是 15 秒一次的公网热路径），
> 页面拿**第一次回执**的值当基准（那一刻磁盘上的就是本页跑着的那份，不会一进来就误报）。
> 为什么非要自动发现：浏览器里的 `app.js` 是打开那一刻的快照，自动刷新只重新拉数据、用的还是旧代码，
> 光靠人手动刷新才会看见改动——「界面改了怎么没生效」不该等人自己想到按 F5。

## 五、求解器指纹：结果的版本归因

指纹 = 求解器源码的**内容哈希**，8 位十六进制。算法只有一份语义，三处实现必须逐字一致：

- 输入文件（顺序固定）：`tools/solver.cpp`、`src/core/Board.cpp`、`src/core/Board.h`，
  加 `src/solver/*.h`（按字典序）。
- 每个文件算 sha256，把 64 位十六进制**无分隔符拼接**，再对拼接结果做一次 sha256，取前 8 位。

三处实现：
1. `CMakeLists.txt:147-162` → `add_definitions(-DSOLVER_VER="xxxxxxxx")`（桌面端/本机 solver）
2. `scripts/dist/package-dist-client.sh` → 裸 g++ 编译时 `-DSOLVER_VER` 手动传（分布式用的三个二进制）
3. `tools/ctl_ui.py:_fingerprint()` → 给版本卡算「当前」和历史（工作区/历史提交两种取字节路径）

链路：`-DSOLVER_VER` 烙进二进制 → `solver --version` 读出来 → 客户端 `probe_solver_ver()`
领任务时就探好、随结果一起交 → 服务器存进 `done[tid].solver_ver` → ctlui/`export` 里可按版本筛。
这条链只覆盖**求解器**；客户端自己那份身份（`client_ver`）是另一条轴，见第六节。

**为什么这么绕**：历史上踩过「发出去的 solver 全报 `dev`」——裸 g++ 不走 CMake，
没有 `-DSOLVER_VER` 就命中 `tools/solver.cpp:13` 的兜底宏。当时那批众包数据完全无法归因，
只能作废重跑。现在打包脚本自己算一遍并显式传，且 `check` 步骤会断言产物里能找到指纹串。

**当前指纹** `7d9d7749`（2026-11-03 起；上一版 `22c22ee6`、再上 `c1f60148`）。
这次变是因为 `tools/solver.cpp` 加了两层番茄钟：本机连算计时（`--pomodoro`）和**按调度相位在局间停下**
（`--pomodoro-phase <anchor>:<连算>:<整轮>`，见第二节）。两层都只往 stdout 多打一行 `{"rest":…,"src":…}`、
局与局之间睡一段。**统计口径不变**：每局的 `t0` 在 `play()` 之前起、`sec` 在 `play()` 之后算，
休息落在这对读数之外，所以逐局的耗时与胜率跟不开番茄钟时同构；变长的是整个任务的墙钟时间，
面板那行「总用时」如实把休息算进去。

> 2026-11-03 已重打并发布：manifest `ver=1793714752`、`solver=7d9d7749`（macOS dmg /
> win64 zip / linux64 tar.gz 三份全发）。发版**不等于机器立刻会歇**——每台机器要等到下一个
> 任务边界自更新换上 solver 才真带上两层番茄钟；换到之前旧包两个参数都不认，
> 客户端会先探再传（一次探两条），探不到就降级为两层都不开并说出来，所以旧包不会被这次改动跑坏。

上一版 `22c22ee6` 只做了本机计时那一层（`--pomodoro`），当天就被用户把口径挪到调度侧，因此从未发布。

上一版 `c1f60148`（2026-11-01）只因为 `src/solver/SolverEngine.h` 加了一行 `#include <climits>`——
Linux/mingw 的 gcc 不像 macOS libc++ 那样隐式携带它，`INT_MAX` 直接编译失败。
纯可移植性修复，胜率行为不变（舰队验收数据见 `docs/求解器第四代报告.md`）。
> 这一版的拥有提交是 `a446afa`，ctlui 求解器版本卡的历史表与「当前」因此对得上。

> 铁律：**改指纹输入文件里的任何一个，指纹必变，就必须重打并发布 solver**；
> 反之只改客户端 Python 不用重编 solver。打包脚本按指纹做缓存，见下节。

## 六、自动更新链路

因为「求解器版本要归因」，新版本 solver 必须能推到已在跑分的机器上，否则舰队永远跑旧版。
但**公开端口 + 零密钥**意味着任何人都能提交结果，更新通道若被中间人替换，就等于把
任意代码发到测试者机器上。所以链路带签名，且**客户端只认哈希、不认版本号**：

1. `scripts/dist/package-dist-client.sh` 末尾生成 `manifest.json`：
   `{"ver": <时间戳>, "files": {"<name>": {"file": "/client/file/<name>", "sha256": ..., "size": ...}}}`，
   用 **Ed25519 私钥**对 `{"ver","files"}` 的规范化 JSON 签名（`sig` 为 base64）。
2. 私钥在打包机 `~/.cmsdist/ed25519-private.key`（0600，**不进仓库、不进 `dist-solver/`**——
   那个目录是要整个发给测试者的成品）；公钥内嵌在客户端源码里。
3. manifest + 各端文件由脚本 `scp -P 712` 上传到 `/var/lib/cmsdist/client/`，
   服务器用 `GET /client/manifest` 与 `GET /client/file/<白名单名>` 原样分发。
4. 客户端在**每个任务边界**拉 manifest、验签，逐文件比对自己的 sha256，
   **只换有差异的文件**，然后 `execv` 重启进入新版本。

onefile（macOS dmg）与免安装包（Win/Linux）在「换文件」这一步差别很大：

- **onefile**：`sys.executable` 就是自身，换文件=换整个包 → 必须重启才生效。
  下载先写 `<exe>.new`，校验后 `os.replace`（**新 inode**）再 `execv`。
- **免安装**：`dist_client.py` 要重启、`solver` 二进制不用（下次领任务就用了新的）。
- **Windows 特殊性**：运行中的文件删不掉但能改名——`os.replace` 失败就先把旧文件挪成
  `.old` 再顶上；`.old` 由任意实例下次启动顺手删。**换到一半断了的现场**（主文件没了只剩 `.old`）
  启动时会先把 `.old` 还原回主文件——删掉等于把最后一份可用字节也毁掉（bat 会报「解压不完整」）。
  solver 二进制被别的窗口占用时**不做挪开兜底**（挪开再换不回去会弄丢主文件），直接等下一轮。

多窗口并发的处理（踩过才写下来的）：
- 更新前先抢锁 `~/cmsdist-update.lock`（`O_CREAT|O_EXCL` 原子占坑，内容=pid+时间戳）。
  判活**只探活、绝不发信号**：Windows 上 `os.kill(pid, 0)` 不是探活——`0` 就是
  `CTRL_C_EVENT`（wincon.h），CPython 的 `os_kill_impl` 先给目标进程组投一次 Ctrl+C，
  投不动（跨控制台/目标无控制台）它不返回，接着 `OpenProcess(PROCESS_ALL_ACCESS)` +
  `TerminateProcess(handle, 0)` 直接把目标杀掉（更新锁判活和 `--status` 都误杀过另一个窗口），
  所以走 ctypes 只申请 `PROCESS_QUERY_LIMITED_INFORMATION` 句柄。pid 判活失效时按 900s 兜底接管孤儿锁。
- 等待窗口空转到锁释放，轮到它时磁盘多半已被第一个窗口换好：逐项重查哈希，命中就**不下载**直接进新版。
- 「我跑的是旧版但磁盘已是目标版」= 别的窗口已换好 → 直接重启白嫖。
- 任何一步失败都静默返回、继续用当前版本跑分——**更新是锦上添花，不是任务的一部分**，绝不因为更新把在跑的任务搞丢。

### 两个身份：solver 指纹只管一半（2026-11-03）

上面第 4 步是**逐文件**换的，于是存在一种只看求解器指纹完全隐形的状态：客户端 `dist_client.py`
换成了新的、`solver.exe` 因为在用换不动还是老的（Windows 上的常态，见上面 `.old` 那段）。
用户当场指出「求解器版本和客户端版本不是一个东西」——所以客户端也报一个身份：

- **算法**：`client_ver()` = 「我这个可执行体」的 sha256 前 8 位，与 manifest **同口径**，
  所以两边能直接对：onefile（mac）取 `sys.executable` = manifest 的 `macos-bin`；
  免安装（win/linux）取包里那个 `dist_client.py` = `win64-py` / `linux64-py`。
  只算一次并缓存——更新走 `execv` 换进程镜像，新进程自己重算。读不到就留空（= 看板上「未上报」），
  **绝不编一个哈希充数**。
- **上报点**：`/claim` 与 `/result` 各一次。领取时进 `inprog`（看板「进行中」那一列），
  交结果时进 `done` 记录与落盘 blob 的 `client` 段（事后归因「这批数据是哪份代码算的」）。
  老客户端两个字段都不发 = 空串，**不是错误也不许变成硬门槛**（照样 200，界面归「未上报」）。
- **展示**：ctlui 卡片改名「版本身份」，「线上在跑」按 **`求解器 · 客户端` 成对**聚合——
  拆成两行会把半更新藏起来（两边各自都只剩一个值，看着像全员一致）；「已发布」那行的客户端是
  **三份**（每平台一份程序字节，一台机器该对哪份取决于它的系统）；「工作区」两个都实算
  （客户端 = `tools/dist_client.py`，与「已发布」对不上就是改了没发）。
  进行中 / 最近结果 / 历史记录三张表各加一列「客户端」，版本历史那两张表也是两列并排（见下条）。
  `distctl.py status` 第一屏一行：`线上在跑: 求解器 X + 客户端 Y ×N 终端`。
- **客户端自己那一屏也两个都印**（2026-11-04）：启动横幅 `solver=…（指纹）  客户端 <哈希>`，
  跑起来以后每个任务头部的 Seed 行 `Seed: … solver X  client Y`。以前 Seed 行只有求解器，
  测试者发来的截图看不出那台是不是半更新；两处都是「有值才印」，读不到就整段不出现，不印「未知」占位。
  这两行只有**用新字节启动的客户端**才画得出来 → 改 `dist_client.py` 就必须重打三平台包重发，
  舰队才会在任务边界换上（光在工作区改、不发布，线上看到的还是旧那份）。
- **提交记录**：「版本历史」那张表**两个身份共用一条时间线**——`git log` 同时跟着求解器那 5 个
  路径和 `tools/dist_client.py`，收录条件是「任一身份变了」，去重也按 `(求解器, 客户端)` **这一对**做
  （分两张表会让人对不上到底换了哪一半）。客户端文件是 2026-10-31 才进仓库的，更早的提交那一格显示
  `—`（= 那时还没有这个文件，不是「未知」，也不许编个哈希填进去）。绿底行要求**两个身份都**等于工作区那份。
  历史按 HEAD 缓存，冷算约 3s（56 条 × 每条现算两份指纹）。
- **生效顺序**分两半：服务端一部署就能开始记（老客户端归未上报），
  客户端那一半要等各机器在任务边界自更新换上才带上。

**两道防「啥都没改也全量假更新」的闸**（重编译产物字节必变：PE 时间戳、PyInstaller 打包时间戳）：
1. 源码指纹没变 → 复用 `~/.cmsdist/build-cache/` 的上次产物，不重编；
   缓存有效性判断的**哈希文件列表必须与 SOLVER_VER 覆盖同一批文件**
   （2026-11-01 就是因为漏了 `Board.h` 和 `src/solver/*.h`，头文件改了还复用旧产物，
   发出过一份「manifest 说指纹 A、二进制里是 B」的不一致版本）。
2. 发布前比对线上 manifest 三个文件的 hash，全一致就跳过发布（`ver` 不动）。

想强制全量重编：`rm -rf ~/.cmsdist/build-cache`。

### 同步盘/网盘目录里的客户端：写入不落地（2026-11-01）

有测试者把 Win 免安装包解压进**科大云盘**直接跑：文件写入报成功、读回来还是旧版
（WebDAV 读缓存或云端旧版把本地顶回去）。对自动更新来说这就是无底洞——
「下载→替换→读回旧版→再下载」原地死循环，还凭空多出 `.old` 文件。

防线：`_upd_verify` 在换完文件后**重新读一遍**比对哈希；还对不上就判定「写入没生效」，
打印明确提示（建议把文件夹移到本地磁盘），置 `_UPD_STUCK`，**本进程此后不再尝试更新**，
继续用当前版本跑分。分发话术里应带一句：**解压到本地磁盘再跑，别放同步盘**。

### 「每次自动更新必出问题」的根因（2026-11-01 结案）

现象：`zsh: killed`，退出码 137，`codesign -v` 却完全合法。
根因：打包脚本 `cp "$BUILD/dist/dist-client" "$OUT/dist-client"`——`cp` 对已存在的目标文件是
**原地写（O_TRUNC，同一 inode）**。macOS 的代码签名按 inode 记账：
一个正被 mmap 执行的二进制，字节被改掉的那一刻这个 vnode 就被内核永久判定无效，
之后每次 exec 都 SIGKILL——磁盘上重新验签是过的，但那个 inode 已经废了。
用户习惯直接从 `dist-solver/` 里跑客户端，客户端在跑分中途自动更新 → 必杀。

三层修复（都已落地）：
1. 脚本：`cp` 前先 `rm -f` 目标，保证换成新 inode。
2. 客户端：启动时记录自身 `st_ino`；若「同 inode 但字节变了」= **原地覆盖，不是正常自动更新**，
   打警告继续用当前版本跑分、**不 execv**（否则一进新版就被拦杀，白丢一个任务）。
3. 已废文件：`rm` 后重新打包一次即恢复。

**How to apply**：以后再报「killed / 137」，先比 inode 与 codesign，别急着怀疑签名逻辑；
任何会顶掉正在运行的二进制的操作，都必须「删了再放」而不是覆盖。

## 八、运维要点

- **管理操作全要口令**，与 cmsgate 同一份；`status` / `export` 不要。
- **`export` 全量在内存拼，是这台机器的高危口子**（2026-11-05 OOM 事故实录，见上面红线）：
  task 级口径用 `admin-status`/`admin-lite`（<1MB），逐局级统计走 `distctl agg`（2026-11-05
  当天补上的流式聚合，只读不要口令；直方图按猜雷次数分桶，桶 100 是 99+ 溢出）。
- **作废优先于删除**：`invalidate` 只翻 `valid` 标记、原始 `.json.gz` 保留，事后能复核；
  `drop` 才是硬删（不回队列、种子作废）——只有确认是垃圾数据才用。
- **`export` 默认排除作废项**，做统计前先确认口径，别把被污染的样本混进去。
- **`kick` 不等于作废**：只是把在跑的收回队列（60s 冷却），结果没交上来自然不存在。
- **改 `lease_sec` 要看任务规模**：专家盘 100 局在慢机器上可能逼近默认 2h，收太紧会把好机器反复打断。
- **healthcheck 第 9 项**打 `/ping`；注意线上探活脚本含 QQbot 段（**不进仓库**），
  重新部署 `scripts/web/deploy-monitor.sh` 前先 diff 保留服务器上的那段。
- **`dist-solver/` 可以整个目录外发**（成品目录）；私钥、构建缓存都在 `~/.cmsdist/`，不在里面。
- **win solver 必须 `-static -s` 全静态**：裸 `x86_64-w64-mingw32-g++` 出来的 exe 导入
  `libstdc++-6.dll` / `libgcc_s_seh-1.dll`，干净 Windows 上双击就是「找不到 libstdc++-6.dll」
  （2026-11-01 Win11 实测：面板停在 `Waiting`、0/10000 局）。只写 `-static-libstdc++` 不够，
  libstdc++ 静态后还拖一个 `libwinpthread-1.dll`。打包脚本编完会 `objdump -p` 断言导入表里
  没有这三个 DLL，命中就中止发版；`-static` 之后只剩 UCRT + KERNEL32（Win10/11 自带）。
- **构建缓存的键含链接参数**：`~/.cmsdist/build-cache/fingerprint` 里除了源码哈希还写了一行
  `LINK:…`。只改 `-static` 这类参数时源码指纹不变，不加这行就会把坏产物原样再发一次。
- **客户端启动即探 solver**：`probe_solver_ver()` 现在区分「跑不起来」（OSError → 致命，
  吭声退出，不领任务）和「老版不认 `--version`」（返回空串，照常跑）。前者若放过去就是
  「领了→0 局→作废→立刻再领」的空转，白烧队列。
- 客户端日志 `~/cmsdist-client.log`，排查测试者问题时让他直接发这个文件。
