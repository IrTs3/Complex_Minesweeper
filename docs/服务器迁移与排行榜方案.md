# 复数扫雷：网页化（服务器部署）与三端排行榜方案

> 版本 v1 · 面向 2 核 2GB 阿里云服务器 + 自有域名
> 原则：**安全第一**（联网前先威胁建模、外部输入不可信、依赖可验证、发布前自查）

> ⚠️ **落地状态（2026-10-25 回写）**：网页化已上线（https://ty0712.com），但实现走的是
> **方案 C（纯 TypeScript 重写）而非本稿推荐的方案 A（WASM）**——2026-10-13 因 Emscripten
> 工具链在本机不可用而改道，core 与 UI 均为 web/ts 独立实现（运行时 wasm_stub.ts 是占位），
> 「共用同一份 core」的承诺由**种子/存档格式对拍测试**维持，不是共享代码。
> ICP 备案已于 2026-10-20 通过；8080 端口已收回环给 nginx 内测自用，排行榜落地须另选端口。
> 本稿其余内容仍是有用的设计参照，但涉及「现状盘点」的行数与端口以回写注释为准。

## 0. 结论速览（TL;DR）

| 问题 | 结论 |
| --- | --- |
| 能否网页化 | **能，而且成本很低**——游戏逻辑已经是纯标准 C++（core/ 共 1857 行，**零 SFML、零平台 API**），可直接编译成 WebAssembly；只需替换表现层（Canvas2D）。（⚠️ 实际落地改走了纯 TS 重写，见页首落地状态注） |
| 服务器够不够 | **绰绰有余**。游戏运算 100% 在玩家浏览器里，服务器只发静态文件 + 排行榜接口，2C2GB 足以支撑很大访问量。 |
| 三端排行榜 | **一套服务端、三端共用协议**。核心是「服务端发种子 + 回放动作校验」，服务端直接复用同一份 core 代码判胜负，作弊面极小。 |
| 网络库怎么选 | **C++ 标准库目前没有网络接口**（Networking TS 至今未入标准）。推荐：抽象出 IHttpClient，桌面端用**系统自带栈**（Windows WinHTTP / macOS NSURLSession），网页端用浏览器 fetch。**零第三方网络依赖**，TLS 交给操作系统打补丁——安全上最稳。 |
| 最大的坑 | ① 国内服务器 + 域名必须 **ICP 备案**，否则 80/443 直接被封；② 上传背景图的**版权**（若来自网络素材，公开分发与网站展示有法律风险）；③ 纯本地计时的排行榜**无法 100% 防时间作弊**，需按档位取舍。 |

## 1. 现状盘点（已实测）

### 1.1 代码分层

| 层 | 文件 | 行数 | 依赖 | 迁移结论 |
| --- | --- | --- | --- | --- |
| **core（规则）** | Board / Cell / ComplexMath / Rabbit / Seed / SaveGame / SetupConfig | **1857** | 仅 std（array, random, vector, cmath, string, cstdint） | **原样编 WASM** |
| ui（渲染/交互） | Renderer.h/.cpp | 4569 | SFML 3 | 用 Canvas2D 前端替换 |
| main（事件循环） | main.cpp | 1163 | SFML + 平台 | 用 JS 事件循环替换 |
| 平台胶水 | FileDialog.mm / FileDialog_win.cpp | 89 | AppKit / Win32 | 网页端改为 input type=file |

**关键事实：core 内没有任何 sf:: 或平台 API**（已 grep 验证）。因此：
- 网页端与桌面端**共用同一份规则实现**，不会出现「网页判赢、桌面判输」的分歧；
- 种子/存档格式（Seed.h 的 encode/decode、SaveGame）本来就在 core，**天然跨端兼容**——同一个种子串在 Win / mac / 网页复现同一局。

### 1.2 资源体积（网页加载预算）

| 资源 | 现状 | 网页建议 |
| --- | --- | --- |
| 主字体 IBMPlexSerif-Regular.ttf | 157 KB | 子集化（只留用到的字形）→ 约 30 KB |
| 中文（仅「红专并进 理实交融」等几处） | 用系统字体 | 子集化 CJK → 约 10 KB |
| 背景图 bg.jpg 1857x1080 | 205 KB | 转 WebP + 降到 1600 宽 → 约 120 KB |
| WASM 核心 | — | 预计 **150–400 KB**（纯逻辑，关异常/RTTI 后） |

首次访问合计约 **300–600 KB**，之后走强缓存。

### 1.3 工具链现状

- 已有：cmake、node/npm（只用于前端打包，不需要 Node 后端）
- 缺：**Emscripten**（brew install emscripten 或官方 emsdk，推荐 emsdk 以便锁版本）

## 2. 目标与约束

**目标**
1. 一个域名（如 https://minesweeper.example.com）打开即玩，桌面/手机浏览器都可用；
2. Win / mac / 网页三端共享排行榜；
3. 尽量不引入新语言栈，服务端也用 C++，降低维护面。

**约束**
- 服务器 2 核 2GB、单机、无专职运维；
- 无账号体系（或极轻量），以匿名昵称 + 客户端 ID 为主；
- **游戏必须能完全离线玩**——排行榜是可选增强，断网不得导致玩不了。

## 3. 总体架构

    玩家浏览器（手机/PC）
    ┌───────────────────────────────────┐
    │ index.html + JS/Canvas2D          │
    │ core.wasm（与桌面同一份规则）      │
    └──────────────┬────────────────────┘
                   │ HTTPS（只有排行榜相关请求）
    ┌──────────────▼────────────────────────────────────────┐
    │ 阿里云 2C2GB（Ubuntu 22.04）                           │
    │                                                       │
    │ nginx :443 —— TLS 终止 / HTTP2 / 缓存 / 限流 / CSP     │
    │   ├── /             → 静态文件（wasm/js/图片/字体）    │
    │   └── /api/ (proxy) → 127.0.0.1:8080                  │
    │                                                       │
    │ leaderboard 服务（C++，仅监听回环）                     │
    │   ├── 复用 core/ 回放动作判胜负（同一份规则）           │
    │   └── SQLite（WAL，单写者）                            │
    │                                                       │
    │ 桌面客户端（Win/mac）= 同一套 /api/ 协议                │
    └───────────────────────────────────────────────────────┘

**要点**
- 服务器**不参与游戏运算**：网页端在浏览器算，桌面端在本机算；服务端只在提交成绩时回放一次动作序列（纯逻辑、微秒级）。
- API 只监听 127.0.0.1，由 nginx 反代——C++ 服务里**不写任何 TLS 代码**，证书与协议细节交给 nginx（少一处出错的地方）。

## 4. 网页版实现路径

### 4.1 三条路线对比

| 方案 | 做法 | 优点 | 缺点 | 评价 |
| --- | --- | --- | --- | --- |
| **A. core→WASM + Canvas2D 自绘** | 只把 core 编成 wasm；JS 画格子 | 规则零改动；体积小；跨端一致；无 SFML 依赖 | 需重写约 800–1200 行绘制/交互（网页比 SFML 简单） | **推荐** |
| B. 用 SDL2 / raylib 重写整层 | 换掉 SFML | 图形代码风格接近 | 要移植 2400 行渲染，还要引入新依赖 | 不划算 |
| C. 全部用 JS/TS 重写 | 抄一遍规则 | 前端最舒服 | **两份规则**，日后必然分叉；种子兼容有风险 | 反对 |

### 4.2 推荐实现（方案 A 细节）

1. **编译**：emcc 只编 core（Board/Seed/SaveGame/ComplexMath/Rabbit），导出 C ABI（见附录 C），用 -O3 -fno-exceptions -fno-rtti，产物 core.wasm + core.js。
2. **渲染**：Canvas2D 绘制网格与文字。桌面端已有布局参数（格子边长、间隙 3px、表头 138px、自适应 40→24px）搬到 JS，保持视觉一致。
3. **输入**：DOM 事件调 wasm。左键开格、右键弹标记菜单（阻止 contextmenu）、**双击开格（chord）**、中键 chord，与桌面一致。
4. **自适应**：沿用桌面规则（优先 40px，不足降 24px），用 window.innerWidth/Height 代替屏幕分辨率。
5. **配色**：网页**不需要** macOS 的 P3 预补偿（displayColor()），直接用 sRGB 十六进制——这点必须在网页端显式关掉，否则颜色会偏。
6. **字体**：IBM Plex Serif 与中文子集用 @font-face 内嵌。
7. **存档/种子**：localStorage 存设置；种子复制粘贴与桌面端**完全互通**（同一套 Base64 + Rabbit）。
8. **触屏**（建议一并做）：长按 = 标记菜单，单击 = 开格，双击 = chord。

### 4.3 需要新增的核心能力（桌面端也受益）

**动作日志（Action Log）**——目前 core 没有记录玩家每一步：

    struct Action { uint8_t type; int16_t r; int16_t c; uint32_t t_ms; };
    // type: 1=开格  2=标记(带类型)  3=chord  4=取消标记

用途：① 服务端回放校验；② 本地存档更小更稳（替代现在「整张棋盘画进 JSON」）；③ 支持录像/复盘。
兼容：保留现有 kind=save 格式的读取能力，新存档走 kind=replay。

## 5. 服务器部署方案（2C2GB 足够）

### 5.1 组件与端口

| 组件 | 说明 |
| --- | --- |
| nginx | 443/80：TLS 终止、静态文件、/api/ 反代、限流、安全头 |
| leaderboard（C++） | 仅 127.0.0.1:8080，systemd 管理，非 root 用户（⚠️ 8080 现已被 nginx 回环内测占用，落地须另选端口，见页首注） |
| SQLite | 单文件 + WAL；每日备份 |
| certbot | Let's Encrypt 自动续期（或用阿里云免费证书） |

未列出的端口一律 UFW 拒绝；SSH 仅密钥登录 + 改端口 + fail2ban。

### 5.2 nginx 关键点（草案见附录 B）

- TLS 1.2+、HSTS、**CSP**（default-src 'self'，禁内联脚本）、X-Content-Type-Options: nosniff、Referrer-Policy: no-referrer
- /api/ 限制请求体（如 64 KB）与速率（limit_req，如 10 r/s 突发 20）
- 静态资源长缓存 immutable；wasm 的 MIME 必须是 application/wasm
- 关闭 autoindex、隐藏版本号

### 5.3 排行榜服务（C++）

- 用 **cpp-httplib**（单头文件、成熟、可固定版本并校验哈希）实现 3 个端点；
- 不推荐「只用 OS 原生 socket + 手写 HTTP 解析」——HTTP 解析是经典漏洞面，手写风险大于收益；
- 入参**严格校验**（长度上限、数值范围、动作条数上限）；JSON 用固定版本、经过审计的小库，并对解析做 fuzz；
- systemd 加固：NoNewPrivileges=yes、ProtectSystem=strict、ProtectHome=yes、PrivateTmp=yes、ReadWritePaths 只给数据库目录。

### 5.4 容量与流量估算

| 项 | 估算 |
| --- | --- |
| 页面加载 | 约 0.5 MB/人（首次），之后命中缓存 |
| 一次提交 | < 10 KB |
| 1000 人/天 | 约 0.6 GB/天（阿里云按流量计费要留意，可上 CDN 或改固定带宽） |
| CPU/内存 | 峰值几乎全在 nginx 静态分发；C++ 服务常驻 < 50 MB |

> 访问量上来后第一个瓶颈是**带宽**而不是 CPU——把静态资源丢对象存储/CDN，服务器只留 API。

### 5.5 合规与法务（务必先办）

1. **ICP 备案**：国内服务器绑定域名对外提供 web 服务，未备案的 80/443 会被拦截。~~备案通过前可先用 IP + 非 80 端口内测~~（**已于 2026-10-20 通过**）。
2. **隐私**：访问闸门的 `usage.jsonl` 目前**明文 IP 与 ip_hash 并存**（管理员要能回答"这条密码是谁在用、从哪来的"，权限与脱敏约定见 docs/密码闸门.md「访问日志与隐私」）；排行榜日志则只存 IP 哈希、不存无关设备指纹；昵称做长度与字符白名单 + 敏感词过滤。
3. **版权**：背景图若来自网络素材，公开网站展示与随包分发都有风险；建议换自制图或明确授权的图。字体 IBM Plex 是 OFL，中文子集嵌入前请确认许可。

## 6. 排行榜：协议与数据模型

### 6.1 API（HTTPS + JSON）

    POST /api/v1/challenge
      请求: { board: "16x16", client_id: "...", platform: "mac|win|web" }
      响应: { token: "<随机128bit>", seed: "<MSD1 种子串>", server_ts: ..., expires_in: 900 }

    POST /api/v1/score
      请求: { token, actions: [...], won: true, elapsed_ms: 42310,
              client_id, nickname, platform, client_version }
      响应: { accepted: true, rank: 7, best_ms: 42310, reason: null }
      失败: { accepted: false, reason: "REPLAY_MISMATCH|TIME_IMPLAUSIBLE|RATE_LIMITED|TOKEN_EXPIRED" }

    GET  /api/v1/leaderboard?board=16x16&sort=time&limit=50&period=all|week
      响应: { rows: [ { rank, nickname, elapsed_ms, actions, platform, created_at } ], updated_at }

    GET  /api/v1/health  →  { ok: true, version }

设计要点：
- **种子由服务端下发**（见 §8），token 与种子绑定、15 分钟过期、一次性使用；
- 只有 won=true 的成绩进榜；失败局可另表统计或丢弃；
- 分榜维度：board（9x9 / 16x16 / 24x16 / 自定义）、sort（用时 / 步数）、period（总榜 / 周榜）。

### 6.2 数据库（DDL 见附录 D）

    runs(id, board, seed_hash, client_id, nickname, platform, client_version,
         elapsed_ms, actions_count, won, created_at, ip_hash)
    索引: (board, won, elapsed_ms)、(board, client_id, elapsed_ms)、(created_at)

- 去重：同一 client_id + board 只保留最好一条（历史可选另存）；
- seed_hash 便于发现「同一种子高频刷榜」的异常；
- 每日 sqlite3 .backup + 异地副本。

### 6.3 身份与昵称

- client_id：首次运行生成 128 位随机值，存本机配置（桌面端 config/settings.ini，网页端 localStorage）。**这不是账号**，只是防刷限流的桶；
- 昵称：长度 1–16、字符白名单（中英文数字下划线）、敏感词过滤、同 IP 限改频次；
- 匿名默认名形如 玩家#7f3a。

## 7. 三端客户端接入

### 7.1 网络层选型（「优先 C++ 标准库」的现实答案）

**必须先说清楚：ISO C++ 至今没有标准网络库。** Networking TS 未进 C++20/23，C++26 也未纳入；sys/socket.h 与 winsock2.h 只是操作系统 ABI，不是 ISO 标准。于是有四条路：

| 路径 | 依赖 | 跨端一致性 | TLS 维护 | 安全评价 |
| --- | --- | --- | --- | --- |
| **① 系统原生栈**（WinHTTP / NSURLSession / fetch） | **零第三方** | 三份薄适配（约 150 行/端） | 操作系统负责并自动打补丁 | **最推荐** |
| ② libcurl | 1 个成熟库 | 一份代码 | 需自建/随包分发，要跟安全更新 | 可以，但 Windows 打包变复杂 |
| ③ cpp-httplib + OpenSSL | 2 个依赖 | 一份代码 | 要自己维护 OpenSSL 版本 | 服务端合适，客户端偏重 |
| ④ Boost.Asio/Beast + OpenSSL | 重依赖 | 一份代码 | 同上 | 过度设计 |

**采用 ①**：桌面端各写一个薄实现，接口统一；网页端直接用 fetch。好处：
- 不引入任何需要长期跟踪 CVE 的第三方网络/加密代码；
- 证书校验、系统代理、TLS 版本策略沿用系统设置（对用户也最友好）；
- 代码量小、审计面小，符合「安全第一」。

### 7.2 抽象接口（三端同一份业务代码）

    struct HttpResponse { int status; std::string body; std::string error; };

    class IHttpClient {
    public:
        virtual ~IHttpClient() = default;
        virtual HttpResponse post(const std::string& url,
                                  const std::string& body,
                                  const std::string& content_type) = 0;
        virtual HttpResponse get(const std::string& url) = 0;
    };

    // 实现：HttpClientWin(WinHTTP) / HttpClientMac(NSURLSession) / HttpClientWeb(fetch)

排行榜业务代码只依赖这个接口，不感知平台。

### 7.3 线程与体验（很重要）

- **绝不在渲染线程里联网**：开 worker 线程 + 请求队列；主循环只取结果（无锁队列或 mutex + 立即返回）；
- 提交时机：结算后异步提交；失败则**离线入队**（本地文件 / localStorage），下次启动或联网时重试（带退避）；
- UI：设置面板加「参与排行榜」开关（默认关）+ 状态提示（已提交 / 离线待传 / 失败）；
- **绝不阻塞、绝不因网络失败影响游戏**——网络模块整体可编译期关闭（-DMS_NO_NETWORK=1）。

### 7.4 请求实现要点

Windows（WinHTTP 伪代码）：

    WinHttpOpen(L"ComplexMinesweeper/1.0", WINHTTP_ACCESS_TYPE_AUTOMATIC_PROXY, 0, 0, 0);
    WinHttpConnect(session, host, 443, 0);
    WinHttpOpenRequest(conn, L"POST", path, 0, WINHTTP_NO_REFERER, ...);
    WinHttpSetTimeouts(h, 5000, 5000, 5000, 5000);      // 必设，避免卡死
    WinHttpSendRequest / WinHttpReceiveResponse / ReadData
    // 校验：status==200、Content-Length 上限（如 256 KB）、先验格式再解析

macOS：NSURLSession + dataTaskWithRequest，同样设超时、限制响应体大小、只接受 https。
两端共同点：**只允许 https、必设超时、响应体限长、失败即丢弃**。

## 8. 反作弊设计（本方案的核心）

### 8.1 威胁模型

| 资产 | 威胁 | 对策 |
| --- | --- | --- |
| 排行榜公信力 | 改客户端、伪造成绩 | **服务端回放动作**，判定胜负与用时 |
| 规则一致性 | 自制「简单棋盘」 | **服务端下发种子**，客户端只能玩服务端给的局 |
| 服务可用性 | 刷接口、超大请求 | 限流、体积上限、动作条数上限、token 一次性 |
| 数据 | 注入、越权 | 参数化查询、不暴露管理接口、只读合成视图 |
| 服务端本身 | 远程漏洞 | 只监听回环、最小依赖、systemd 沙箱、定期更新 |

### 8.2 主流程：服务端发种子 + 动作回放

1. 客户端 POST /challenge → 服务端生成 seed（随机 rngSeed + 标准行列雷数）、记录 token 与 server_ts；
2. 玩家游玩，core 记录动作日志；
3. 结算后 POST /score（token + 动作 + 声称结果）；
4. 服务端：
   - 用**同一份 core 代码**（编译进服务端）decodeSeed → Board → 依序回放动作；
   - 校验：动作是否合法（不能开已开格、不能标记已开格、chord 前置条件）、最终是否真的胜利；
   - elapsed_ms 用**服务端时间差**（receive_ts - issue_ts）与客户端自报值交叉校验：自报值 ≤ 服务端时间差 + 容差，且 ≥ 动作数 x 物理下限；
   - 通过才入榜，token 立即失效。

> 这一步消灭绝大多数作弊：**客户端无法让服务端相信一个不可能的局**，因为判定用的是服务端自己的规则实现。

### 8.3 用时可信度（三档，按需求取舍）

| 档位 | 机制 | 防作弊强度 | 代价 |
| --- | --- | --- | --- |
| **L1 宽松** | 本地计时 + 合理性校验 | 中（可把时间改大） | 实现最轻 |
| **L2 推荐** | 服务端时间差做上限 | 较高 | 中途长时间挂机会失效，需明示规则 |
| **L3 严格** | **逐动作上报**（每步 POST 或 WebSocket） | 高（服务端掌握节奏） | 必须联网玩，流量与实现成本上升 |

建议：**网页端默认 L3**（反正要联网，成本天然低）；**桌面端默认 L2**，并允许在设置里参加「严格榜（需联网）」。两榜分开展示，避免规则混淆。

### 8.4 反滥用

- 每 IP / 每 client_id：挑战 10 次/分钟、提交 5 次/分钟（nginx limit_req + 应用层双保险）；
- 动作数量上限（如 ≤ 3 x 棋盘格数）、请求体 ≤ 64 KB；
- 同一 token 只能用一次；异常模式（同种子高频、秒级满分）自动进观察队列；
- 排行榜日志不记敏感信息，仅记 IP 哈希与拒绝原因（访问闸门自己的 `usage.jsonl` 另存明文 IP，两者不混用）。

## 9. 安全加固清单（可直接当 checklist）

**服务器**
- [ ] SSH：禁密码登录、改端口、fail2ban、仅密钥
- [ ] UFW：只放行 80/443（+ SSH 端口）
- [ ] 系统与 nginx 自动安全更新
- [ ] 服务用专用非 root 用户，systemd 沙箱开启
- [ ] 排行榜服务仅监听 127.0.0.1
- [ ] SQLite 文件权限 600、目录 700
- [ ] 每日备份 + 定期演练恢复
- [ ] 证书自动续期并监控到期

**应用**
- [ ] 所有输入：长度/范围/枚举校验（宁可拒绝，不要「尽力解析」）
- [ ] JSON/种子解析：固定版本依赖 + fuzz + 解析失败即拒绝
- [ ] 回放：格子上限、动作上限、时间上限，防 CPU/内存放大
- [ ] 错误信息不泄漏内部细节（对外统一 reason 枚举）
- [ ] 依赖固定版本 + 校验哈希（下载脚本同样适用）

**客户端**
- [ ] 只允许 https，拒绝降级
- [ ] 超时必设（连接/发送/接收）
- [ ] 响应体上限，先验格式再解析
- [ ] 排行榜默认关闭，需用户主动开启
- [ ] 不发送设备指纹/位置/无关信息；昵称白名单过滤
- [ ] 发布前检查包内是否夹带 config/（个人设置与路径）等敏感文件

## 10. 实施路线图

| 阶段 | 内容 | 产出 | 验收 |
| --- | --- | --- | --- |

## 11. 风险与未决问题

1. **ICP 备案周期**（通常 1–2 周）是关键路径，建议立刻启动（**2026-10-20 已通过，此项已闭环**）；
2. **背景图版权**：公开发布前必须确认授权，否则换图；
3. **L2/L3 用时的规则公平性**：桌面端可暂停计时（切窗口/开面板），若服务器按墙钟计上限，需在规则里明确「挂机超过 X 分钟成绩不计」；
4. **CDN 与国内访问**：备案后建议静态资源走 CDN，显著降低带宽账单；
5. **手机触屏**：右键标记在触屏不可用，需长按菜单（建议 P2 一并做）；
6. **原生移动包**：本方案不覆盖，后续可用 Capacitor/Tauri 包一层网页版。

## 12. 与原「安全第一」原则的对应

| 原则 | 本方案的落实 |
| --- | --- |
| 联网前先威胁建模 | §8.1 威胁模型表 |
| 能不用网络就不用 | 游戏本体完全离线可玩；网络模块可编译期关闭；服务端不承载游戏运算 |
| 外部输入不可信 | §9 应用清单：长度/范围校验、解析失败即拒绝、回放有上限 |
| 依赖可验证 | 客户端零第三方网络依赖；服务端只用固定版本单头文件库并校验哈希 |
| 凭据不进代码 | 无服务端鉴权密钥硬编码（种子密钥仅用于分享压缩，不作为鉴权）；token 随机、一次性 |
| 发布前自查 | §9 客户端清单最后两项 |

      SELECT board, client_id, MIN(elapsed_ms) AS best_ms
      FROM runs WHERE won = 1 GROUP BY board, client_id;
