## 一、项目是什么

**ComplexMinesweeper（复数扫雷）** 是一个纯 C++20 + SFML 3 的桌面游戏。

它把经典扫雷的提示规则「周围有 N 颗雷」换成了**「周围雷的复数和的模长」**：

```
提示 = |Σz| = √(realSum² + imagSum²)
```

地雷有四种类型：`+1` / `−1` / `+i` / `−i`。因为是**带符号求和**，不同类型的雷会相互抵消——一颗 `+1` 和一颗 `−1` 挨在一起，复数和恰好是 0。

这带来整个游戏最关键的设计差异：

| 经典扫雷 | 复数扫雷 |
| --- | --- |
| 数字 0 = 周围没雷 = 安全 | 数字 0 = 复数和抵消成 0，**周围可能有雷** |
| 数字 N = 周围恰好 N 颗雷 | 数字 N = 周围雷的复数和的模长，**实际雷数可能大于 N** |
| 计数信息唯一确定 | 模长信息**丢失了相位**，需要联立多个方程反推 |

所以黄色 `0` 不代表安全区，这是复数扫雷最狠的陷阱。玩家必须把周围所有提示联立起来，才能解出每颗雷的精确复值。

**项目状态**：`LICENSE` 尚未选定，正式发布前补充（README 已于 2026-10-22 去掉「Beta 测试阶段」的表述）。
**平台**：macOS (Apple Silicon) 原生 + Windows x64（在 macOS 上交叉编译）。
**其他特征**：游戏本体零联网（无网络栈、无遥测、无运行时下载）；无第三方 JSON 库（手写解析）。
> 唯一会联网的是**另一条链路**：`tools/dist_client.py`（跑分客户端）与 `web/` 网页版的验密闸门。玩家拿到的游戏 exe/dmg 里没有任何出站请求。

## 二、核心玩法机制

### 2.1 复数提示的显示规则

提示的显示形式与颜色由 `realSum` / `imagSum` 的组合决定：

| 显示 | 含义 | 颜色 |
| --- | --- | --- |
| 空白 | 周围**完全没有雷**（唯一会连锁展开的情况） | — |
| 黄色 `0` | 周围有雷但复数和完全抵消 —— **有雷、不展开** | 黄（#EFE430） |
| `+1` / `−2` | 纯实和（`imagSum == 0`），带符号显示 | 蓝 |
| `+i` / `−3i` | 纯虚和（`realSum == 0`），带符号显示 | 绿 |
| `√2` / `√5` / `5` | 实虚混合，只给模长（最简根式或勾股整数） | 紫 |

分类逻辑在 `ComplexMath.h` 的 `hintKind()`，返回 `Empty` / `PureReal` / `PureImag` / `Mixed` 四种 `HintKind`。

**一个必须理解的区分**：`realSum` 和 `imagSum` 是**有符号**的，而 `minesAround` 是**总数**。只有 `minesAround == 0` 才触发连锁展开。「显示为 0」和「周围没雷」是两回事。

### 2.2 双判胜口径

除了传统的「翻开全部安全格」，复数扫雷还有一条**标记判胜**路径——即使安全格没翻完，只要标记方案能解释所有可见提示，也算赢。由 `Board::gaugeConsistent()` 统一分发到两套口径：

```cpp
// Board.cpp:494
bool Board::gaugeConsistent() const {
    return magnitudeMode_ ? allMinesFlaggedMagnitudeConsistent()
                          : allMinesFlaggedGaugeConsistent();
}
```

**① 有符号口径（默认）** `allMinesFlaggedGaugeConsistent()`（`Board.cpp:368`）

要求非常严格，分三步：

1. **union-find 连通分量**（`:372-410`）：被同一个「已开且带提示」格看到的雷互相 union，形成若干分量
2. **锚定表**（`:412-430`）：某分量里的实雷若被「纯实提示格」看到，则该分量的实轴**不允许整体取反**
3. **校验**（`:432-464`）：
   - 标记总数必须**恰好等于**雷数（多标少标都不算）
   - 每颗雷都要有标记
   - **轴必须一致** —— 给实雷标虚标记直接判负
   - 同一分量内取向必须整体一致
   - 被锚定的轴不得取反

未被锚定的分量允许整体取反（`+1 ↔ −1`），因为那种情况下提示本身就无法区分两种取向——这是数学上正确的要求，不是宽容。

**② 模长口径** `allMinesFlaggedMagnitudeConsistent()`（`Board.cpp:470`）

勾选「总是显示模长」时启用。玩家看不到符号，判据放宽为：每颗雷有标记，且每格的 `|Σ雷|` 恰好等于其邻域 `|Σ标|`。用模长平方比较，避免开根号：

```cpp
// Board.cpp:488-489
const int sMine = x.realSum * x.realSum + x.imagSum * x.imagSum; // 真实和的模长² = 可见提示
if (reF * reF + imF * imF != sMine) return false;                // 标记和的模长² 必须吻合
```

`setMagnitudeMode()`（`Board.cpp:501`）支持局中切换：棋盘状态全保留，且不剥夺已成立的胜利。

### 2.3 其他交互规则

- **首点安全**：布雷发生在首点。棋盘 ≥ 雷数+9 时，首点**九邻域**（八邻域 + 自己）无雷；否则只排除点击格
- **chord 双击开格**：比经典扫雷更严格——要求**逐颗** `flag == mine`，而非「旗子数量 == 数字」就够了。失败可配置为静默 / 提示 / BOOM 三态
- **种子分享**：明文 JSON → Rabbit 流密码（RFC 4503）→ Base64。完整复现 = 种子 + 首点坐标（首点不同则布雷位置不同）
- **计时**：首点翻开后才走表；切窗口 / 开面板自动暂停

### 2.4 游戏难度有多难

`docs/求解器统计_300局定稿.txt` 的数据（复数 vs 经典反事实对照，同棋盘同首点；猜格按每格精确含雷率取最小风险）：

| 难度 | 复数胜率 | 复数零猜胜率 | 经典胜率 | 经典零猜胜率 |
| --- | --- | --- | --- | --- |
| Easy 9×9×12 | 96.0% | 41.3% | 93.7% | 80.7% |
| Medium 16×16×40 | 29.7% | **2.0%** | 87.7% | 68.3% |
| Hard 24×16×72 | **0.7%** | 0.0% | 67.3% | 33.7% |

复数提示在 Medium/Hard 极难零猜推进；但反过来，「标记推进」式的胜局是复数口径独有的胜利路径（Medium 占其胜局的 28.7%）。

> **2026-10-24 大样本定稿（当前最可信口径）**：seed=20261024，Easy 3000 局 **94.4%**、
> Medium 1000 局 **64.7%**、Hard 500 局 **17.4%**；经典对照 92.8% / 87.0% / 66.4%。
> 与旧 seed=20261008 的六个数字**全部落在 ±3.4 点内**，统计可复现、无 seed 依赖。
> 详见 `docs/求解器统计_大样本定稿.txt`。
>
> 早先的 P0+P1 口径报过 Medium 65.6% / Hard 14.0%，样本更小 —— **Hard 100 局的 14.0% 是样本波动**
> （500 局给出 17.4%，σ≈1.7%），别再拿它当基线。上面那张表是 300 局口径的历史定稿，
> 同样不要混着比。演进过程与差距分析见 `docs/求解器统计_P0P1对照.txt`。
>
> **Hard 差的那 6 个点，原假设已被 2026-10-24 的 P2 实测否定**：曾以为是「DP 分量没有 profile、
> 吃不到全盘雷数约束」，但插桩量出来 `absorb` 平均 193 里 `interior`（不接触线索的内部格）占 191.4、
> DP 分量只占 1.6，且判据在 97.5% 的 analyze 里恒真。为验证该假设写的分量级支撑集零收益（已默认关闭）。
> 随后用真值做无偏校准，证明**概率本身是准的甚至偏保守**，Hard 的瓶颈是「每局本来就要猜十几次」
> 而不是算得不准（60 局测得 14.4 次/局，大样本 500 局为 16.5 次/局）—— 详见该文档「原假设被实测否定」一节。
>
> **2026-10-24 的 P3 又排除了两条结构性猜想，当前代码仍是最优版本（= P2 状态）**：
> ① 盘末「按轴收口」—— 触发条件在 Medium 100 / Hard 60 局里出现 **0 次**（是恒等式，非运气），代码已删；
> ② 从吸收池扣掉 DP 分量边际 —— **明确负收益**（Hard 150 局 13.3%→10.7%，Medium 500 局配对 23:7，p≈0.006），
> 根因是 DP 解集为超集导致 `ΣcellProb` = 真实雷数的 **2.24×**，且吸收池 91% 本就是内部格、无稀释可修，已逐字回退。
> 两条的实测数据、为什么必然失败、以及新增的「理论存活上界 / 猜格校准表」两个观测口径，都在
> `docs/求解器统计_P0P1对照.txt` 的「P3」一节 —— **再提同类改动前先读那里**。
>
> **2026-10-30 第四代已取代 P2 状态**：A1/A2 分层 BucketDP（DP 分量按雷数 profile 分层输出精确权重，
> 修掉 2.24× 边际高估并接入全局推理）+ C1 自适应 DP 阶梯 + C2 三贪心消元序 + **宽 9 解锁**，
> 复数口径大样本 Easy 94.6% / Medium 87.8% / Hard 67.3%（与经典口径统计平手）。详见 `docs/求解器第四代报告.md`。

### 2.5 求解器提示（自动解答）——未随发布版提供

> 2026-10-22 裁决：**暂不写进部署 / 打包版本**，先在文档里记录，待复核后再决定是否开放。

实现留在 `src/solver/SolverEngine.h` + 桌面端 `main.cpp`（`MS_SOLVER_HINTS` 开关，当前为 **0**）：

- **看什么**：只用屏幕上可见的信息（已翻开格的数字、玩家的标记、表头两轴计数），不读雷区。
- **给什么**：先找可证安全格（P=0）或必雷格（P=100%，带类型）；都不可证时，按**每格精确含雷率**给出全盘风险最低的猜测格。
- **概率口径**：FULL 分量按 profile 分层计数 + 前后向二维卷积，把内部格并入二项吸收池；卷积超预算或存在降级分量时退回采样估计，并在文案前加 `≈` +「（估计）」。采样连含雷解都没找到时显示「未知」，**不等于 0**。
- **交互**（评审版才有）：H 键触发；结果格脉冲高亮，盘面一变（翻开/标记数变化）或终局即撤；坐标 (行, 列) 从 0 开始。
- **开关**：`src/desktop/Renderer.h` 的 `#define MS_SOLVER_HINTS 0`。发布版为 0：不注册 H 键、帮助页不列该条、不画高亮；使用说明里也不提。评审时改为 1 重新编译即可。

相关数据见 `docs/求解器统计_300局定稿.txt`（猜格按最小含雷率选取）。

## 五、关键实现机制

### 5.1 复数提示计算 `Board.cpp:204`

一次遍历同时算出「有符号复数和」与「总数」两个维度：

```cpp
switch (at(rr, cc).mine) {
case MineType::P1: re += 1;  ++n; break;   // +1
case MineType::M1: re -= 1;  ++n; break;   // -1
case MineType::Pi: im += 1;  ++n; break;   // +i
case MineType::Mi: im -= 1;  ++n; break;   // -i
}
x.realSum = re; x.imagSum = im; x.minesAround = n;
```

`realSum` / `imagSum` 有符号，`minesAround` 是总数——这三者组合才构成完整的提示信息。

### 5.2 首点安全布雷 `Board.cpp:162`

```cpp
const bool shieldNeighbors = mines_ <= total - 9;
banned[safeR * cols_ + safeC] = 1;
if (shieldNeighbors) { forEachNeighbor(safeR, safeC, [&](int rr, int cc){ ... banned[...] = 1; }); }
rng_.shuffle(candidates.data(), candidates.size());   // Rng.h 自写 Fisher-Yates，跨端逐位一致
```

棋盘不够大时退化为只排除点击格。随机分型用 `typePick(rng_)`（1~4 等概率，四种雷各约 25%）；指定分型则造池洗牌（`signFlip` 定符号 + `rng_.shuffle`），保证数量精确。洗牌与取随机数**一律走 `src/core/Rng.h`**，不用 `std::shuffle`/`std::uniform_int_distribution`——那些实现跨平台不保证逐位一致，会破坏跨端同种子同雷局（见 5.12）。

**标记不排除布雷**——标记只是猜测，不影响布雷随机数消耗，这是与经典扫雷一致的行为。

### 5.3 连锁展开只认总数 `Board.cpp:136`

```cpp
x.opened = true;
if (x.minesAround == 0) {   // 黄 0（复数和抵消但有雷）走到这里什么都不做
    forEachNeighbor(...);   // 只有"周围雷总数 = 0"才扩散
}
```

关键在于判定用的是 `minesAround` 而不是 `realSum/imagSum`。黄色 `0` 会被翻开但**不扩散**，也不会被误判成安全区。

### 5.4 chord 双击比经典严格 `Board.cpp:84`

```cpp
// 有符号口径：标记类型必须逐颗一致；模长口径：看不到符号，有任意标记即可
const bool ok = magnitudeMode_ ? (n.flag != MineType::None) : (n.flag == n.mine);
if (!ok) allFlagged = false;
```

经典扫雷的 chord 只要求「周围旗数 == 数字」。这里要求逐颗 `flag == mine`——因为在复数世界里，标错一颗的类型会导致整个联立方程解错。

### 5.5 最简根式 `ComplexMath.h:15`

`largestSquareFactor` 抽出最大平方因子 f，使 s = f²·r 且 r 无平方因子，然后 r==1 输出整数、否则输出 `f√r`：

```cpp
const int f = largestSquareFactor(s);
const int r = s / (f * f);
if (r == 1) return std::to_string(f);
return (f > 1 ? std::to_string(f) : std::string()) + "\u221A" + std::to_string(r);
```

所以 √8 会显示为 `2√2` 而不是 `√8`。`\u221A` 是 √ 的 Unicode 码点（避免源码里直接写非 ASCII）。

### 5.6 Display P3 色彩补偿 `Renderer.cpp:30`（macOS 专属坑）

macOS 把 SFML 窗口 framebuffer 按 Display P3 解释，直接填 sRGB 十六进制会偏艳（`#66CCFF` 实测显示成 `(46,207,255)`）。所有颜色经 `displayColor()` 做 sRGB → 线性 → P3 矩阵 → sRGB 的往返补偿，用户自定义图片解码后走 `applyDisplayP3()`（用 4096 级查表加速）。Windows 不补偿。

### 5.7 文字清晰度 hack `Renderer.cpp:262`

SFML 3 的字体纹理默认线性过滤，且**没有公开 API 关闭**，文字发虚。解法是 `const_cast` 后逐尺寸关闭：

```cpp
for (unsigned size = 8; size <= 48; ++size)
    const_cast<sf::Texture&>(font_.getTexture(size)).setSmooth(false);
```

集中在 `textSpr` / `textTLSpr` / `textCJKSpr` 三处，字体加载后也对 8~48 号预设置一遍。

**不要再走 RenderTexture 预渲染的老路**——README 明确记录该方案在 SFML 3.0 实测会让文字整片变白块。

### 5.8 种子与加密

`Seed` 结构（`Seed.h:38`）以 `magic = "MSD1"` 开头，含 `firstRow` / `firstCol`（**必须复现首点，否则布雷位置不同**）、`kind = "new" | "save"` 区分新开局与进度存档。

密钥硬编码在 `Seed.h:36`：

```cpp
inline constexpr const char* kSeedMagic = "MSD1";
inline constexpr const char* kSeedKey = "TY0712#66ccff";
```

加密链是 **可读 JSON → Rabbit 流密码 → Base64**。README 明确声明这是**分享用的压缩 + 轻量混淆，不是安全边界**——密钥硬编码在二进制里，`strings` 即可读出。未来排行榜的反作弊靠「服务端下发种子 + 动作日志回放验证」，不靠这层加密。

**Rabbit 三个易错点**（`Rabbit.h` 内均有注释）：

1. 子密钥 K0 取密钥**最高** 16 位（`key[14]||key[15]`，大端）
2. 128 位输出块按**整体大端字节串**（16 位字按 `s[7..0]` 倒序）
3. 计数器异或后**不要**再多迭代 4 次（会变成 §A.2 的 IV=0 向量）

### 5.9 网页版 canvas 铺满视口 + 顶栏的两套坐标

**背景铺满整屏但不拉伸**：`Renderer::drawImageCover` 用
`sc = max(winW / iw, winH / ih)` 取较大缩放比——**等比缩放、只裁切，永不拉伸**。
canvas 铺满视口后，背景自然铺满整屏。

但「铺满」要改**两处**，只改一处无效：

| 位置 | 改前 | 作用 |
| --- | --- | --- |
| `game.ts` `availSize()` | `innerWidth - 24` | 传给渲染器的**可用区** |
| `renderer.ts` `computeLayout()` | `winW = max(640, boardW + 2*kPad)` 再按 mx* 收窄 | 真正决定 canvas 大小 |

第二处是关键：`availSize` 传的视口宽只被当作**上限**用，
不改它canvas 仍然只比棋盘宽一点（实测 709×847，视口 1440×900）。

**顶栏的「局部坐标 vs 窗口坐标」**：顶栏绘制包在
`ctx.translate(sideX, headerTop)` 里，内部坐标全部保持原设计值
（那套 y = 9/16/54/86/92/96/109/111/116/127 是手工排布的六行网格，逐个加偏移必错）。
代价是 `computeLayout` 存下来的 `Rect` 变成**局部坐标**，而鼠标命中拿的是窗口坐标，
所以统一用 `absTop(r)` 换算，涉及 `headerActionAt` / `bgHitZone` / `bgMove` / `seedRects`。

> ⚠️ 改这类手工排版代码**不要逐个坐标加偏移**：要translate 就整体translate，
> 要改就先用 CDP `Runtime.evaluate` 量出每个元素的真实 `Rect` 再动手。
> 我曾把 `drawPill(x, w, …)` 的**宽度当成 y**、把 y 编成 `sy0+62` 这类想当然的值，
> 连续翻车 5 次；最后靠量数据才定位准。

`sideX` 让顶栏两侧与**棋盘边缘**对齐（不是窗口边缘），否则宽屏上顶栏会贴到屏幕两端、
比棋盘宽出一大截。顶栏另加一层半透明底板——背景铺满后深色小字压在浅色建筑上会糊。

#### 顶栏的行位表 `kRow`（窄屏重排后）

**所有 y 只有一份来源：模块级 `renderer.ts` 的 `kRow`。任何地方都不许再写死 y。**

| 行 | y | 左 | 右 |
| --- | --- | --- | --- |
| row1 | 16 | 标题 + 帮助键 | 难度键排 / 重开 |
| row2 | 54 | 药丸 MINES LEFT / TIME | CUSTOM / SEED / 齿轮 |
| row3 | 94 | 图例（芯片换行时为其让位） | 计数芯片 ±1 / ±i |
| row4 | 118 | OPACITY 标签 + 数字框 + 滑块（trackY=128） | — |
| row5 | 150 | 统计文字（barY=170 进度条） | — |
| row6 | 176 | 三个复选框（**独占整行**） | — |

`kHeaderH = 204` 是**由内容反推**的，不是拍脑袋：最后一行 176 + 16 + 下留白。

这里踩过三个坑，都属于同一类「尺寸不是由内容决定」：

1. **顶栏被棋盘挤窄**。原式 `sideX = max(bx, (winW-620)/2)`，于是顶栏可用宽
   `rx = min(棋盘宽, 620)`。窄窗口里棋盘只有 429，顶栏也就只剩 429，而内容仍要 620
   → 标题撞难度键、OPACITY 数字框压复选框文字（800×600 实测）。
   改为取**最小** sideX（即最宽的顶栏）并夹到不越界。

2. **药丸冲出顶栏**。药丸被硬编码 `y=116`、高 28px → 铺到 144，而当时 `kHeaderH=138`。
   既出界，又压住统计行（111）与进度条（127）。**1440 宽下就已存在**，是截图才看出来的。

3. **芯片"放不下就跳过"**。第一版这么写，结果 `±i` 芯片直接不画了——
   **信息丢失比布局难看严重**。正确做法是换行到 row3，并让图例自动缩短。

> 闸门是 `web/test/header-overlap.mjs`：实测 1440/1024/800/640 四个尺寸的**两两矩形重叠**，
> 外加「有没有控件被挤出视口」（防止用越界换不重叠）。
>
> ⚠️ **探针的几何必须按源码公式算，不能手编**。第一版我给芯片/进度条编造了固定宽度，
> 于是它先报"全绿"（假绿）、改完代码又报"没修好"（假红），白跑了好几轮。
> **探针自己会撒谎，这是比被测代码更常见的失败模式。**

### 5.10 四道输入校验闸门

种子/存档是从外部粘贴进来的**文本**，图片是朋友分享 config 目录时带进来的**文件** —— 两类都得校验：

| 防护 | 位置 | 防什么 |
| --- | --- | --- |
| `seedIsSane()` | `Seed.h:63` | 超大棋盘申请爆内存（`cols=99999` 会申请约 199 GB 必崩）。注意 `realMines/imagMines == -1` 是「随机分型」的合法哨兵值，不能当非法值拒收 |
| `ms::imgprobe`（`ImageProbe.h`） | `ImageProbe.h:53` | **图片解压炸弹**：70 字节的 PNG 可以声明 20000×20000，解码要约 2.1 GB（stb 只挡 >2^31 那档），解码时再 resize 一份 → 峰值约 4.2 GB → 未捕获 `bad_alloc` 直接 terminate。所以**先按字节卡 24 MiB**（`kMaxBytes`，解码前），**再从文件头读宽高卡总像素 ≤ 4096×4096**（`kMaxPixels` / `sizeOk`，判定用 `w*h` 而不是长边）；顺带拒绝符号链接与未知格式（fail-closed） |
| `safeImageName()` | `SettingsIO.cpp:54` | `settings.ini` 里的路径穿越（防借 RESTORE ALL 删配置目录外文件）。除 `/ \ ..` 外还挡 Windows 盘符冒号与设备名（`C:foo.png` 是盘符**相对**路径） |
| `cellAt()` 钳上界 | `Renderer.cpp:514` | 点窗口边距产生「幽灵格」越界读 |

**图片这一道的结构性保证**（光有闸门函数不够，得保证没人能绕过去）：

- `Renderer::loadImageChecked` 是 `src/desktop` 里**唯一**的解码入口，
  四条加载路径（背景 / 四标记 / 空白格 / 内置背景图）全部经它；
- 它**不做 `probeFile(path)` 再 `loadFromFile(path)` 的两次 open** —— 那是 TOCTOU：
  验过的那份字节和真要解码的那份可能不是同一个文件。现在是
  `readWholeFile`（stat → 拒软链 → 卡 24 MiB → 一次读出）→ 验头 → `loadFromMemory(同一份缓冲区)`；
- `src/desktop` 内 `sf::Image::loadFromFile` 的调用点数为 **0**（连 `loadFromMemory` 也只允许出现在
  `loadImageChecked` 里）；这条由 `tools/check_invariants.py` 的 84 项静态断言钉死 ——
  将来谁新加一处裸解码，脚本会直接报错，而不是让闸门静默失效。
- 超限时的提示**带实际尺寸**：桌面端与网页端同一口径，写明实际宽×高与约多少万像素，
  而不是一句笼统的 `bad image`。

### 5.12 跨端一致的布雷 RNG `src/core/Rng.h` ↔ `web/ts/rng.ts`

**这一节的每条规则都是规格，不是实现建议。改任一端必须同时改另一端。**

#### 为什么不能用 `<random>`（原实现错在哪）

原C++ 端是 `std::mt19937` + `std::shuffle` + `std::uniform_int_distribution` + `std::bernoulli_distribution`。
看起来标准、实际不可复现，原因是后三者**全是实现定义**的：

| 库 | 平台 | `std::shuffle` 怎么洗 |
| --- | --- | --- |
| libc++ | macOS / iOS | 自成一套 |
| libstdc++ | Linux / MinGW | 又一套 |
| MSVC | Windows | 第三套 |

`std::mt19937` 本身是标准确定的（位运算可复刻），但**只要经由那些 distribution 取数就又变了**。
所以原实现在同一颗种子下，macOS 上的存档拿到 Linux 上打开就是另一张图——
**桌面端自己在跨平台时都是坏的**，不只是"网页抄不上C++"。

#### 现在的做法：两端共用一份自写算法

| 环节 | 选型 | 为什么 |
| --- | --- | --- |
| 状态扩展 | SplitMix32 → 128 位 | xoshiro 的标准初始化法 |
| 取数 | **xoshiro128\*\*** | 全 32 位运算；JS 侧用 `Math.imul` + `>>> 0` 精确复现，**不需要 BigInt** |
| 有界整数 | **拒绝采样** | 直接 `% n` 有模偏差：前 `2^32 % n` 个取值各占双倍权重 |
| 洗牌 | Fisher–Yates，**从后往前**（`i = n-1 → 1`） | 方向也属于规格，反了就对不上 |

`2^32 % n` 在两端都靠无符号回绕算：`(0 - n) % n`，即 `(2^32 - n) % n`——
与 `2^32 % n` 相等（商少1、余数不变）。C++ 侧靠 `uint32_t` 的回绕是良定义的，JS 侧靠 `>>> 0`。

**取数顺序同样是规格**：洗牌 → `signFlip`/`typePick` 的调用次序变了就是另一个雷局。

#### 回归闸门


## 六、构建与分发全链路

### 6.1 三条产线

```
① macOS 开发线（动态链接 Homebrew）
   brew install sfml cmake → scripts/game/build.sh → cmake-build-debug/ (Ninja, Debug)

② macOS 发布线（自包含 .app）
   scripts/game/package.sh → build-release/ (Ninja, Release, -O3 -DNDEBUG)
   → 拷 dylib → 改 @rpath + 删 Homebrew rpath → ad-hoc 重签 → zip + dmg + SHA256SUMS

③ Windows 线（在 macOS 上交叉编译，全静态）
   brew install mingw-w64 → scripts/game/build_windows.sh
   → build-freetype-win/ → third_party/freetype-win/   (libfreetype.a)
   → build-sfml-win/      → third_party/sfml-win/       (4 个 .a)
   → build-win/           → minesweeper.exe (3.3 MB, GUI 子系统, -static, --strip-all)
   → dist/ComplexMinesweeper-win64/{exe,assets,说明} + zip + SHA256SUMS
```

两条发布线的依赖策略**完全相反**：macOS 用 Homebrew 动态库 + 手工改 rpath 做自包含；Windows 用 MinGW 静态库直出单文件（额外 `-static-libgcc -static-libstdc++`，否则干净 Windows 上双击即启动失败）。

### 6.2 构建矩阵表

| 目录 | 平台 | 生成器 | 类型 | 用途 |
| --- | --- | --- | --- | --- |
| `build/` | macOS arm64 | Unix Makefiles | Debug | 早期手工构建遗留，含求解器批量实验输出与 `.dSYM` |
| `cmake-build-debug/` | macOS arm64 | **Ninja**（CLion 内置） | Debug | CLion 默认日常开发目录，`build.sh` 的输出目标 |

### 6.4 覆盖率流程

### 6.5 打包的验签闸门

`package.sh` 的签名流程是层层递进的，每一环失败都立即删产物终止：

1. 签名 → 2. `--strict` 验签 → 3. `_CodeSignature` 目录落盘断言
→ 4. **从成品 zip 解包再独立验签** → 5. dmg 挂载复验 → 6. SHA256SUMS

脚本注释记录了历史教训：原先三处 `codesign` 行尾的 `|| true` 会吞掉签名失败，产出「打包显示成功、换台机器起不来」的坏包。

打包前还会 `find "$BUNDLE" -type d -name config -prune -exec rm -rf {} +` 清除开发者本机配置，避免个人设置泄漏。

### 6.6 供应链防护

第三方依赖**版本固定**：SFML 3.0.2 与 FreeType 2.13.2 的官方 tarball 提交于 `third_party/`，构建脚本对一切来源（本地 / 直连 / ghproxy 镜像）**强制 sha256 一致才使用**，不符即删并换源、全败终止。

防的攻击场景很具体：代理镜像被黑或链路 DNS 污染，把后门源码无感知编进分发 exe。

### 5.13 种子明文解析：两端同规格（P11，2026-10-22）

**问题**：同一颗种子串，桌面端和网页端解出的棋盘**可能不同**。

根因不是「两端各有个小 bug」，而是**两套完全不同的解析器**：

| | 修复前桌面端 | 修复前网页端 |
| --- | --- | --- |
| 实现 | 手写扫描器（`seedJsonField` / `seedJsonIntClamped` / `seedJsonStringArray`） | V8 的 `JSON.parse` |
| `"cols": 9.5` | **回退默认值 9**（合法棋盘） | **NaN**（`NaN < 5` 与 `NaN > 300` 都是 false，`seedIsSane` 全是比较式判断、没有 `Number.isFinite` 兜底 → NaN 全部通过 → 空棋盘） |
| `"cols": true` | 回退默认值 | `Number(true) = 1` |
| `"cols": 1e2` | 回退默认值 9 | 100 |
| 重复键 | 取**先**出现的 | 取**后**出现的 |
| 尾随逗号 / 尾随垃圾 | 宽容 | 拒绝 |

结果：排行榜要「服务端回放玩家动作日志校验成绩」就无从谈起 —— 回放出来的雷局和玩家实际玩的对不上。

**修法**（两端同时）：

1. 桌面端新增 `src/core/SeedJson.h`：**递归下降的严格 JSON 解析器**（header-only，不链 SFML），语义对齐 V8 `JSON.parse` —— 拒绝尾随垃圾 / 尾随逗号 / 前导零 / `+1` / `.5` / `5.` / `0x10` / `NaN` / `Infinity` / 未转义控制字符 / 非法 `\u` 转义；重复键取后者且**位置保持首次出现处**；数字按 IEEE754 双精度；空白仅 `空格/\t/\n/\r`；孤立代理项解为 U+FFFD；深度上限 `kMaxDepth = 200`。
2. 两端统一为 **fail-closed 契约**：数字必须**有限整数**、布尔必须真布尔、字符串必须纯 ASCII、禁止嵌套容器、越界即拒收 —— **绝不静默回退默认值、绝不产生 NaN**。
3. 「扁平形状」规则（`seedJsonFlatObject` / `isFlatObject`）禁止嵌套容器：这样**任何嵌套输入都被同一条规则拒收**，深度上限只影响拒收理由、不影响判定，消除两端上限差异造成的分歧。

**回归闸门**：`build/seedparse`（C++）与 `web/test/seed-parse-parity.mjs`（TS）**逐字节对拍** 30 例：

```bash
cd build && cmake --build . --target seedparse && cd ..
node web/test/seed-parse-parity.mjs
#    期望：30/30 cases match（C++ ↔ TS ↔ 期望值）
```

用例表覆盖：正常 new/save、手动分型、缺字段（走默认值）、以及 **8 类修复前的分歧点**（`9.5` / `true` / `1e2` / 字符串 `"9"` / `null` / 重复键 / 尾随逗号 / 尾随垃圾），另加 magic 错 / kind 错 / 非对象顶层 / 非法 JSON / 非 ASCII / 尺寸越界 / 首点越界 / rngSeed 越界 / 旧存档 `elapsedSec` / 存档行长度不符 / phase 非法 / 数组混非字符串 / 空对象 / 负维度 / 缺 magic。

> **用例 JSON 由程序拼出来**（`nineRows()` / `buildNew()`），**不手写字符串字面量**。手写 `R"(...)"` 时数组的 `]` 极容易漏 —— 漏了之后整个用例文本变成非法 JSON，两端一起 REJECT，用例就白写了（本项第一版就踩过：case 3 的 `opened` 数组少了 `]`，两端都 REJECT 而期望值写着 ACCEPT）。
>
> 另一处坑：C++ 里 `0xFFFFFFFF` 是 `unsigned`（4294967295 > int 上限），赋给 `int` 会溢出成 `-1`。`kRngSeedMax` 必须写成 `4294967295LL`。
>
> 这条闸门**验证过它真能抓错**：修复前 case 3 / 7 / 10 / 24 全部报警，正是那 5 类分歧点。
